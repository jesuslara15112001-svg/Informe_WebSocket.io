1. Introducción

En las páginas y aplicaciones web actuales, muchas veces necesitamos que los datos se actualicen al instante, como pasa en un chat, un marcador en vivo o el rastreo de un vehículo. En el HTTP tradicional, la comunicación funciona como preguntar y responder: el navegador (cliente) pide algo y el servidor contesta. Si el servidor tiene un dato nuevo, no puede mandarlo solo a menos que el cliente esté preguntando a cada rato (polling) o deje una petición abierta esperando.

El protocolo WebSocket (regla oficial RFC 6455) soluciona esto creando una "tubería" abierta y constante entre el cliente y el servidor sobre una misma conexión TCP. Una vez que se abre ese canal, ambos pueden enviarse mensajes al mismo tiempo (full-duplex), ida y vuelta, sin tener que repetir encabezados pesados en cada mensaje.

2. ¿Cómo funciona WebSocket?

WebSocket trabaja encima de TCP, lo que asegura que los datos lleguen completos y en orden. Se usa con ws:// cuando la conexión no va cifrada y con wss:// cuando va protegida con cifrado seguro (TLS/HTTPS).

2.1 El apretón de manos inicial (Handshake)

Para empezar, el cliente manda una petición HTTP normal pidiendo "cambiar de idioma" a WebSocket mediante las líneas Upgrade: websocket y Connection: Upgrade, junto con una clave de prueba (Sec-WebSocket-Key). Si el servidor está de acuerdo, responde con el código 101 Switching Protocols y una respuesta de confirmación (Sec-WebSocket-Accept). A partir de ese momento, la conexión ya queda lista para enviar mensajes directos. 

GET /chat HTTP/1.1
Host: ejemplo.local:8080
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

2.2 Cómo viajan los mensajes (Tramas)

Ya abierta la conexión, la información no viaja como páginas HTTP completas, sino dividida en pequeños paquetes llamados tramas, que son muy livianos:

  • FIN: Dice si es el último pedazo del mensaje (1) o si viene otro pedazo después (0).
  • RSV1, RSV2, RSV3: Espacios reservados para funciones extra; normalmente quedan en 0.
  • Opcode: Indica qué tipo de paquete es: texto, datos binarios, un mensaje de cierre, o un aviso de prueba (ping y pong).
  • MASK: Indica si el contenido va "revuelto" con una clave (enmascarado). Por seguridad, lo que envía el cliente hacia el servidor siempre lleva máscara.
  • Payload Length: Indica el tamaño del mensaje que se está enviando.

3. Diferencia con otras formas de comunicar

No siempre hace falta WebSocket; a veces basta con otras opciones más simples según lo que necesite el sistema:

4. ¿Dónde se usa y qué hay que cuidar?

4.1 Ejemplos de uso

  • Chats y trabajo en equipo: Mensajes al instante, saber quién está conectado o ver cuándo alguien está escribiendo.
  • Sensores, GPS y monitoreo: Ver en tiempo real la ubicación de un vehículo, el estado de una máquina o lecturas de sensores.
  • Juegos y finanzas: Movimientos rápidos en juegos en línea o cambios de precios al momento.

4.2 Cuidados importantes al implementarlo

  • Consumo en el servidor: Como la conexión queda abierta, muchos usuarios conectados a la vez consumen memoria. Si crecen las visitas, se usan varios servidores coordinados (por ejemplo con Redis) para repartir los mensajes.
  • Seguridad: En internet siempre se debe usar wss:// (cifrado), revisar de qué página viene la conexión (Origin) y validar quién se conecta.
  • Conexiones "zombi": A veces el internet se corta sin avisar; por eso se envían señales periódicas (ping/pong) para saber si la conexión sigue viva y volver a conectar si hizo falta.

5. Conclusión

En resumen, WebSocket es una herramienta muy práctica cuando necesitamos que el cliente y el servidor conversen de ida y vuelta en tiempo real sin perder tiempo ni ancho de banda repitiendo peticiones. Bien configurado —con conexión segura wss://, control de acceso y manejo de reconexiones— permite construir aplicaciones ágiles, rápidas y confiables.
